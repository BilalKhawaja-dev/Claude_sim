# Requirements Document

## Introduction

Claude Simulator is a single-user AI chat platform that replicates the Claude.ai experience, powered by AWS Bedrock Claude models (Sonnet 4 and Opus). The system features RAG-enabled conversations with persistent memory, image understanding and generation, automated session summaries via email, and a full DevOps infrastructure on AWS EKS. The platform is designed as a personal AI assistant that learns and personalizes responses over time through vector-based memory retrieval.

## Glossary

- **Chat_Interface**: The Next.js frontend component that displays the conversation thread, accepts user input, and renders streaming AI responses
- **Backend_API**: The Python FastAPI service that handles all business logic, Bedrock integration, RAG retrieval, and data persistence
- **Bedrock_Client**: The component within Backend_API that communicates with AWS Bedrock for LLM inference, embeddings, and image generation
- **RAG_Engine**: The component within Backend_API that performs vector similarity search against pgvector to retrieve relevant context for AI responses
- **Memory_Store**: The pgvector-enabled PostgreSQL tables (user_memory, embeddings, session_summaries) that store vector embeddings for retrieval
- **Session_Manager**: The component within Backend_API that tracks conversation idle time, triggers summary generation, and manages the 30-day session lifecycle
- **Auth_Server**: The Keycloak instance running on EKS that handles user authentication via OIDC
- **Email_Service**: The SES integration within Backend_API that sends session summary emails
- **Image_Processor**: The component within Backend_API that handles image uploads for vision analysis and image generation requests via Bedrock Titan
- **Conversation**: A single chat session between the user and the AI, consisting of an ordered sequence of messages
- **Message**: A single exchange unit within a Conversation, containing a role (user or assistant), text content, and optional image attachments
- **Embedding**: A 1536-dimensional vector representation of a text chunk, generated by Bedrock Titan Embeddings v2
- **User_Memory**: Manually entered facts and preferences stored in the Memory_Store that the user manages through the Settings page
- **Session_Summary**: An AI-generated summary of a Conversation, created either on idle timeout or before 30-day expiry

## Requirements

### Requirement 1: Chat Messaging with Streaming Responses

**User Story:** As the user, I want to send messages and receive streaming AI responses in real time, so that I have a fluid conversational experience similar to Claude.ai.

#### Acceptance Criteria

1. WHEN the user submits a message through the Chat_Interface, THE Backend_API SHALL send the message along with conversation history and RAG context to the Bedrock_Client for inference.
2. WHEN the Bedrock_Client receives a response stream from AWS Bedrock, THE Backend_API SHALL forward each response chunk to the Chat_Interface via Server-Sent Events within 200ms of receiving the chunk.
3. WHEN the Chat_Interface receives a response chunk, THE Chat_Interface SHALL append the chunk to the current assistant message and render it immediately.
4. THE Chat_Interface SHALL display a visible typing indicator while the Bedrock_Client is streaming a response.
5. WHEN the user submits a message, THE Backend_API SHALL store both the user message and the completed assistant response in the messages table with the correct conversation_id, role, content, and timestamp.
6. IF the Bedrock_Client encounters an error during inference, THEN THE Backend_API SHALL return a structured error message to the Chat_Interface with an error code and human-readable description.
7. IF the SSE connection drops during streaming, THEN THE Chat_Interface SHALL display an error notification and provide a retry option.

### Requirement 2: Model Selection

**User Story:** As the user, I want to toggle between Claude Sonnet 4 and Claude Opus models, so that I can choose between faster responses and higher quality responses.

#### Acceptance Criteria

1. THE Chat_Interface SHALL display a model selector that allows the user to choose between Claude Sonnet 4 (default) and Claude Opus.
2. WHEN the user changes the selected model, THE Chat_Interface SHALL send the model identifier with the next message request to the Backend_API.
3. THE Backend_API SHALL use the model identifier from the request to invoke the corresponding Bedrock model (anthropic.claude-sonnet-4-20250514 or anthropic.claude-opus).
4. THE Chat_Interface SHALL display the currently selected model name in the UI at all times.
5. WHEN the user changes the model mid-conversation, THE Backend_API SHALL use the newly selected model for subsequent messages within the same Conversation.

### Requirement 3: Conversation Management

**User Story:** As the user, I want to create, view, and delete conversations, so that I can organize my chat sessions.

#### Acceptance Criteria

1. WHEN the user clicks the new conversation button, THE Chat_Interface SHALL create a new Conversation via the Backend_API and display an empty chat thread.
2. THE Chat_Interface SHALL display a sidebar listing all Conversations ordered by most recently updated, showing the conversation title and last activity timestamp.
3. WHEN the user selects a Conversation from the sidebar, THE Chat_Interface SHALL load and display the full message history for that Conversation.
4. WHEN the user deletes a Conversation, THE Backend_API SHALL remove the Conversation, its Messages, and its associated Embeddings from the database.
5. THE Backend_API SHALL auto-generate a conversation title from the first user message using the Bedrock_Client when a new Conversation receives its first message.
6. WHILE a Conversation has zero messages, THE Chat_Interface SHALL display a welcome prompt with suggested conversation starters.

### Requirement 4: RAG-Enabled Contextual Responses

**User Story:** As the user, I want the AI to recall relevant information from past conversations and my stored preferences, so that responses are personalized and contextually aware.

#### Acceptance Criteria

1. WHEN the user sends a message, THE RAG_Engine SHALL generate an Embedding of the message using Bedrock Titan Embeddings v2.
2. WHEN the RAG_Engine has generated the message Embedding, THE RAG_Engine SHALL query the Memory_Store for the top 5 most similar chunks across the embeddings, user_memory, and session_summaries tables using cosine similarity.
3. WHEN the RAG_Engine retrieves relevant context, THE Backend_API SHALL inject the retrieved context into the system prompt sent to the Bedrock_Client.
4. WHEN a complete assistant response is received, THE Backend_API SHALL chunk the user-assistant exchange into segments of 500 tokens or fewer and store each chunk with its Embedding in the Memory_Store.
5. THE RAG_Engine SHALL return results with a cosine similarity score of 0.7 or higher to ensure relevance of retrieved context.
6. IF the RAG_Engine finds no results above the similarity threshold, THEN THE Backend_API SHALL proceed with the Bedrock_Client request without additional RAG context.

### Requirement 5: User Memory Management

**User Story:** As the user, I want to manually add, edit, and remove personal facts and preferences that the AI remembers, so that I can control what the AI knows about me.

#### Acceptance Criteria

1. THE Chat_Interface SHALL provide a Settings page with a text area where the user can enter personal facts and preferences as User_Memory entries.
2. WHEN the user saves a User_Memory entry, THE Backend_API SHALL generate an Embedding for the entry and store both the text and Embedding in the user_memory table.
3. WHEN the user updates an existing User_Memory entry, THE Backend_API SHALL regenerate the Embedding and update both the text and Embedding in the user_memory table.
4. WHEN the user deletes a User_Memory entry, THE Backend_API SHALL remove the entry and its Embedding from the user_memory table.
5. THE RAG_Engine SHALL include User_Memory entries in every similarity search performed during chat message processing.
6. THE Chat_Interface SHALL display all current User_Memory entries on the Settings page with edit and delete controls for each entry.

### Requirement 6: Session Idle Summary and Email

**User Story:** As the user, I want to receive an email summary of my chat session after 5 minutes of inactivity, so that I have a record of the conversation without needing to check the app.

#### Acceptance Criteria

1. WHILE a Conversation is active, THE Session_Manager SHALL track the time since the last message in that Conversation.
2. WHEN 5 minutes have elapsed since the last message in a Conversation, THE Session_Manager SHALL invoke the Bedrock_Client to generate a summary of the Conversation.
3. WHEN the Session_Manager has generated a Session_Summary, THE Email_Service SHALL send the summary as a formatted HTML email to the user's verified SES email address.
4. IF the Email_Service fails to send the email, THEN THE Session_Manager SHALL retry the send operation up to 3 times with exponential backoff.
5. IF the user sends a new message before the 5-minute idle threshold, THEN THE Session_Manager SHALL reset the idle timer for that Conversation.
6. THE Session_Manager SHALL store the generated Session_Summary in the session_summaries table regardless of email delivery success.

### Requirement 7: Session Lifecycle and 30-Day Expiry

**User Story:** As the user, I want conversations to be visible in the app for 30 days and then archived to long-term memory, so that the UI stays clean while knowledge is preserved.

#### Acceptance Criteria

1. THE Session_Manager SHALL run a daily background job that identifies Conversations older than 30 days from their last message timestamp.
2. WHEN a Conversation is identified as expired, THE Session_Manager SHALL generate a Session_Summary using the Bedrock_Client if one does not already exist.
3. WHEN a Session_Summary exists for an expired Conversation, THE Session_Manager SHALL generate an Embedding for the summary and store it in the session_summaries table.
4. WHEN the Session_Summary and its Embedding are stored, THE Session_Manager SHALL delete the Conversation, its Messages, and its chunk Embeddings from the database.
5. THE session_summaries table SHALL retain Session_Summary records indefinitely to serve as long-term memory for the RAG_Engine.
6. THE Chat_Interface SHALL only display Conversations that are within the 30-day retention window in the sidebar.

### Requirement 8: Image Understanding

**User Story:** As the user, I want to upload images in chat and have the AI analyze and describe them, so that I can get AI assistance with visual content.

#### Acceptance Criteria

1. THE Chat_Interface SHALL provide a file upload control that accepts image files in PNG, JPEG, GIF, and WebP formats up to 5MB in size.
2. WHEN the user uploads an image with a message, THE Backend_API SHALL encode the image as base64 and include it in the Bedrock_Client request as a multimodal message.
3. WHEN the Bedrock_Client processes a multimodal message, THE Backend_API SHALL stream the response to the Chat_Interface using the same SSE mechanism as text-only messages.
4. THE Chat_Interface SHALL display uploaded images inline within the conversation thread alongside the user's text message.
5. IF the user uploads a file that exceeds 5MB or is not a supported format, THEN THE Chat_Interface SHALL display a validation error and reject the upload.
6. THE Backend_API SHALL store a reference to the uploaded image in the Messages table associated with the corresponding Message.

### Requirement 9: Image Generation

**User Story:** As the user, I want to request AI-generated images during chat, so that I can get visual content created on demand.

#### Acceptance Criteria

1. WHEN the user sends a message requesting image generation, THE Backend_API SHALL detect the image generation intent and invoke the Bedrock Titan Image Generator.
2. WHEN the Bedrock Titan Image Generator returns a generated image, THE Backend_API SHALL send the image data to the Chat_Interface for display.
3. THE Chat_Interface SHALL render generated images inline within the conversation thread as part of the assistant's response.
4. IF the Bedrock Titan Image Generator returns an error, THEN THE Backend_API SHALL return a descriptive error message to the Chat_Interface explaining the failure.
5. THE Backend_API SHALL store generated images and associate them with the corresponding Message in the messages table.

### Requirement 10: Authentication and Authorization

**User Story:** As the user, I want secure authentication so that only I can access the chat platform.

#### Acceptance Criteria

1. WHEN an unauthenticated user accesses the Chat_Interface, THE Chat_Interface SHALL redirect the user to the Auth_Server login page.
2. WHEN the user successfully authenticates with the Auth_Server, THE Auth_Server SHALL issue a JWT access token and refresh token using the OIDC PKCE flow.
3. WHEN the Chat_Interface makes a request to the Backend_API, THE Chat_Interface SHALL include the JWT access token in the Authorization header as a Bearer token.
4. THE Backend_API SHALL validate the JWT access token against the Auth_Server's JWKS endpoint on every request.
5. IF the JWT access token is expired or invalid, THEN THE Backend_API SHALL return a 401 Unauthorized response.
6. WHEN the access token expires, THE Chat_Interface SHALL use the refresh token to obtain a new access token from the Auth_Server without requiring the user to log in again.
7. THE Auth_Server SHALL enforce brute-force protection by locking the account after 5 consecutive failed login attempts for 15 minutes.

### Requirement 11: Application Health and Monitoring

**User Story:** As the user, I want to monitor the health and performance of the platform through dashboards, so that I can identify and troubleshoot issues.

#### Acceptance Criteria

1. THE Backend_API SHALL expose a /metrics endpoint in Prometheus format containing request count, request duration, and error rate metrics.
2. THE Backend_API SHALL expose a /health endpoint that returns HTTP 200 when the service is operational and can connect to RDS and Bedrock.
3. WHEN Prometheus scrapes the /metrics endpoint, Prometheus SHALL store the metrics and make them available for querying via PromQL.
4. THE Grafana instance SHALL provide pre-configured dashboards for Backend_API request metrics, Kubernetes cluster health, and RDS database performance.
5. IF the /health endpoint returns a non-200 status, THEN Kubernetes SHALL restart the Backend_API pod according to the configured liveness probe policy.

### Requirement 12: Container Orchestration and Deployment

**User Story:** As the user, I want the application deployed on Kubernetes with proper containerization, so that the system is resilient and demonstrates production-grade DevOps practices.

#### Acceptance Criteria

1. THE frontend application SHALL be packaged as a Docker container image using a multi-stage build with Node 20 Alpine as the base image.
2. THE backend application SHALL be packaged as a Docker container image using a multi-stage build with Python 3.12 slim as the base image.
3. THE EKS cluster SHALL organize workloads into separate namespaces: claude-simulator for application services, auth for Keycloak, and monitoring for Prometheus and Grafana.
4. WHEN a new container image is pushed to ECR, THE CI/CD pipeline SHALL update the corresponding Kubernetes Deployment to use the new image.
5. THE Kubernetes Deployments SHALL include resource requests and limits for CPU and memory on all pods.
6. THE Kubernetes Deployments SHALL include liveness and readiness probes for all application pods.

### Requirement 13: Infrastructure as Code

**User Story:** As the user, I want all AWS infrastructure defined as code using Terraform and all Kubernetes configuration managed by Ansible, so that the environment is reproducible and documented.

#### Acceptance Criteria

1. THE Terraform configuration SHALL provision the VPC, subnets, EKS cluster, RDS instance, ECR repositories, ALB, IAM roles, security groups, and SES email identity.
2. THE Terraform state SHALL be stored in an S3 bucket with DynamoDB locking to prevent concurrent modifications.
3. THE Ansible playbooks SHALL deploy Keycloak, Prometheus, Grafana, and the application Helm charts to the EKS cluster.
4. THE Ansible playbooks SHALL configure the Keycloak realm, client, and user for the claude-simulator application.
5. WHEN the Terraform configuration is applied to a new AWS account, THE configuration SHALL create a fully functional infrastructure environment without manual intervention.
6. WHEN the Ansible playbooks are run against a provisioned EKS cluster, THE playbooks SHALL produce a fully configured and operational application stack without manual intervention.

### Requirement 14: CI/CD Pipeline

**User Story:** As the user, I want an automated CI/CD pipeline that tests, builds, and deploys changes, so that I can ship updates reliably.

#### Acceptance Criteria

1. WHEN code is pushed to the main branch, THE GitHub Actions pipeline SHALL run backend tests (pytest) and frontend tests (jest).
2. WHEN all tests pass, THE GitHub Actions pipeline SHALL build Docker images for the frontend and backend applications.
3. WHEN Docker images are built, THE GitHub Actions pipeline SHALL push the images to the corresponding ECR repositories.
4. WHEN images are pushed to ECR, THE GitHub Actions pipeline SHALL update the Kubernetes Deployments on EKS to use the new image tags.
5. THE GitHub Actions pipeline SHALL authenticate to AWS using OIDC federation without storing long-lived AWS credentials in GitHub.
6. IF any pipeline stage fails, THEN THE GitHub Actions pipeline SHALL halt execution and report the failure with logs.

### Requirement 15: Security

**User Story:** As the user, I want the platform to follow security best practices across all layers, so that my data and infrastructure are protected.

#### Acceptance Criteria

1. THE RDS instance SHALL be deployed in a private subnet accessible only from the EKS cluster's security group.
2. THE EKS pods SHALL access AWS services (Bedrock, SES, ECR) using IAM Roles for Service Accounts (IRSA) with least-privilege policies.
3. THE RDS instance SHALL have encryption at rest enabled using AWS-managed KMS keys.
4. THE Backend_API SHALL store no credentials, API keys, or secrets in source code or environment variables directly; all secrets SHALL be managed through Kubernetes Secrets or AWS Secrets Manager.
5. THE ECR repositories SHALL have image scanning enabled on push to detect known vulnerabilities.
6. THE ALB SHALL terminate TLS connections using a self-signed certificate, ensuring all external traffic is encrypted in transit.
